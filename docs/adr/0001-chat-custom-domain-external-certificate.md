# ADR-0001: Chat-only custom domain via Route.spec.tls.externalCertificate

- Status: accepted
- Date: 2026-11-02
- Scope: `module-hsworkshop` (OpenWebUI chat only)

## Context

OpenWebUI is reachable only on the cluster domain
(`openwebui-hsworkshop.apps.kpicl2-pool-rft8p.aws.rh-ods.com`). We want an optional,
chat-only public hostname `chat.hsworkshop.fous.ai` with trusted HTTPS, without touching
Langfuse, Insights, the model, or global cluster ingress settings. The domain
`hsworkshop.fous.ai` lives in the Cloudflare-authoritative zone `fous.ai` (verified live;
`hsworkshop.fous.ai` itself is **not** a delegated zone). The cluster runs OCP 4.21 with
the cert-manager Operator 1.20.1 installed. The user approved Kubernetes Secret
provisioning for the DNS-01 token (no secret manager).

## Decision

1. **Native `Route.spec.tls.externalCertificate.name`** referencing the cert-manager-managed
   Secret `openwebui-custom-tls`, on a new Route `openwebui-custom` (edge termination,
   redirect). The original Route stays untouched. No custom controller that copies keys or
   manages `secretName`; if a cluster did not support `externalCertificate`, we would stop
   and report evidence rather than install infrastructure.
   - Supported on OCP 4.21: feature gate `RouteExternalCertificate` is in the Default
     feature set (promoted Apr 2025); requires Secret type `kubernetes.io/tls` with
     `tls.crt`/`tls.key`, same namespace as the Route, no inline `tls.certificate`/`tls.key`,
     and router SA read access to that Secret.
2. **Namespaced ACME `Issuer` + `Certificate`** in `hsworkshop` (not ClusterIssuer), with a
   Cloudflare DNS-01 solver reading the token from Secret `cloudflare-dns01`
   (key `api-token`). Certificate SAN is exactly `chat.hsworkshop.fous.ai`.
3. **Least-privilege router RBAC**: a namespaced `Role` with `get,list,watch` on `secrets`
   restricted by `resourceNames: [openwebui-custom-tls]`, bound to the router service
   account `openshift-ingress:router`. No blanket secret access, no cluster-scoped roles.
4. **Ordinary Kustomize overlay** (`module-hsworkshop/overlays/custom-domain`) on the
   existing base `install/`, generated by a deterministic, non-secret renderer
   (`module-hsworkshop/domain/render.sh`; explicit environment beats `config.env`, which
   is parsed — never sourced — and all inputs are validated). The base renders identically
   with or without the overlay; activation is an explicit Argo CD source-path change.
5. **Two-phase activation**: Phase 1 pre-provisions the certificate only
   (`overlays/custom-domain/certificate-only/`, self-contained, no Route/RBAC) so the
   production `Certificate` is `Ready` before the custom Route exists; Phase 2 activates
   the full overlay. Sync waves (-2 certificate, -1 RBAC, 0 Route) order objects within a
   sync but are **not** relied upon for readiness: whether Argo CD health-gates
   `Certificate` was not verifiable offline. Staging validation happens in Phase 1 with
   **no browser route**: the staged certificate is inspected from the issued Secret with
   `openssl x509`, never trusted in a browser. After switching the `issuerRef` to
   production, a possibly-stale `Ready` condition is explicitly **not** trusted:
   activation is gated on decoding the issued Secret's certificate and confirming the
   issuer is a Let's Encrypt **production** CA with the exact SAN (a revision bump and a
   production `CertificateRequest` corroborate). The production render is **committed
   and pushed before** the Argo source-path change.
6. **Token handling**: the Cloudflare token never enters Git. It is applied out-of-band by
   `apply-custom-domain-secret.sh`, which validates context and server before reading the
   token, reads it hidden (or from file/stdin; a missing file is an error), rejects
   whitespace/malformed tokens, never passes it in argv, uses **server-side apply without
   `--force-conflicts`** (no last-applied annotation embedding the token, no forced
   ownership), writes only the named Secret, and restarts no shared controllers.
7. **DNS**: Cloudflare **DNS-only** (not proxied) CNAME to the router's public hostname,
   so the OpenShift router terminates TLS with the issued certificate.
8. **ACME environments**: staging by default (untrusted certificates — validation only);
   production is an explicit re-render performed only after staging validates, so a live
   public hostname never carries a staging certificate unintentionally. Production
   readiness is confirmed by inspecting the **served** certificate (issuer + SAN), not by
   Secret readiness alone.
9. **OpenWebUI settings**: set `WEBUI_URL` to the chat URL, `WEBUI_SESSION_COOKIE_SECURE=true`,
   `WEBUI_SESSION_COOKIE_SAME_SITE=lax`; keep both origins in `CORS_ALLOW_ORIGIN` during
   transition. Signup policy unchanged. Known limitation: OpenWebUI does not redirect the
   alias host to the canonical host.

## Consequences

- Exactly five objects are added by the overlay; removing them is a documented, targeted
  deletion including the TLS Secret (private key) and ACME account-key Secrets, using
  `--ignore-not-found` (the Application runs with `prune: false`, so no broad prune).
- Activation ordering is a hard rule: **commit and push the overlay before changing the
  Argo CD source path**, and patch **only `sources[0].path`** (JSON patch) so the model
  source array is never replaced.
- The Cloudflare token must be zone-scoped to `fous.ai` (cannot be scoped to a
  non-existent `hsworkshop.fous.ai` zone).
- Activating or deactivating the overlay restarts the OpenWebUI pod (Deployment env
  patch); both Routes keep serving during transitions.
- Live cluster-side verification (CRDs, router SA, cert-manager operand readiness,
  feature-gate state) remains a prerequisite for activation because the available
  credentials were expired at implementation time; it is recorded as a blocker, not assumed.
- Future TLS-consumers in this namespace can reuse the pattern but must add their own
  narrow `resourceNames` Role entries.
